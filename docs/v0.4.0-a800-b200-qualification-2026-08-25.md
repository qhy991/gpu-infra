# KernelInfra v0.4.0 A800/B200 qualification — 2026-08-25

> here is closed by KernelInfra v0.5 and agent-gpu-broker v0.6. See the

## Verdict

KernelInfra v0.4.0 implementation commit
`9d862c56a4e9d7c0fbe3f5b57d9e4af08b2bea96` passed exact-source
qualification on both A800 and B200:

- A800 exercised the complete real CUDA path for vector addition and RMSNorm:
  bounded NVCC compile, correctness, compute-sanitizer memcheck/racecheck,
  balanced AB/BA timing, image identity, and frontier reduction. An incorrect
  RMSNorm control was rejected before sanitizer and benchmark.
- B200 exercised a broker-held PTXBench/FIBServe service with live deployment
  attestation, one valid request, two concurrent agent requests sharing one
  worker GPU, KDA authoritative-report import, and Docker containerd manifest
  identity.

These are infrastructure and operator-level results. The FIBServe candidate was
correct but substantially slower than its reference, the KDA record lacks
absolute timings, and the RMSNorm gain is not an end-to-end inference claim.

## Fail-closed controls

Pre-release live integration exposed three real failures, all recorded as
infrastructure errors rather than correctness or performance evidence:

1. a control daemon inherited from an old tmux server could not read the broker
   socket; the request stopped before FIBServe;
2. an entry point named `kernel.cu::run` disagreed with the immutable
   `candidate.cu` snapshot; FIBServe returned HTTP 422 before GPU execution;
3. a hand-built service launch omitted the existing compatibility preload and
   saw both libcudart 12 and 13; the submitted task failed with unknown validity.

The accepted deployment used the existing PTXBench launch wrapper and exact
compatibility/config hashes. No Docker socket permission or broker socket mode
was weakened.

## Final resource state and remaining boundary

The B200 FIBServe job was explicitly stopped after evidence capture. Physical
GPU 0 was idle, the service URL was closed, and no Kernel Infra service job
remained; unrelated KDA and foreign work on other GPUs was left untouched. The
exact B200 control session `kernelinfra-control-gh-9d862c5` remains available
without holding a GPU.

The current broker status schema does not expose the admitted command or
environment. Kernel Infra can bind launch/config/compatibility hashes in the
task and verify live broker/service/source custody, but it cannot independently
prove that the broker launched those exact arguments until the broker emits a
command/environment digest. This is the remaining deployment-attestation gap.
Other deliberate exclusions remain hostile multi-tenancy, global cross-host
scheduling, automatic agent spawning, and end-to-end inference promotion.
