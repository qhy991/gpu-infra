## Snapshot-versus-authority race

A B200 FIBServe deployment became ready and node-status advertised its
deployment id. Before fleet transport reached the target submit, its configured
60-second idle grace elapsed. Fleet selection had legitimately observed ready,
but target node authority rechecked current state and rejected submit as
`state=stopped`.

The route receipt retained:

- selected node B200;
- the ready probe observation;
- installed immutable bundle id
  `fa0b9f44e993db62c991c677cf8cf199`;
- remote rejection error;
- null run locator;
- route digest
  `fa9aa8bf02543a2acc56e13f3ebf02b70fb84de9aa7677163f6c05fe5169c4ac`.

No run was created. This proves routing snapshots are not allocation or
deployment-validity promises and the node daemon remains final authority.

## Remaining qualification gate

A800 remained unreachable throughout v0.9 validation. Its catalog observation
and unknown exclusion are qualified, but installing the exact node daemon and
routing a real A800 CUDA run are not. The feature must not be called dual-node
execution-qualified until that live route succeeds.

Fleet v0.9 also transports task/candidate inputs only. Tasks must use absolute
remote evaluator cwd paths; evaluator/source/toolchain installations remain
node-owned. There is no global queue, automatic retry/failover after target
acceptance, or copied global frontier.
