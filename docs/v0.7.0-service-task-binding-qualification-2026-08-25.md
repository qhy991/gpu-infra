## Binding contract

The checked task template places two reserved tokens in exactly one service
stage:

- `${KERNELINFRA_SERVICE_IDENTITY}` in `judge.identity`;
- `${KERNELINFRA_DEPLOYMENT_RECEIPT}` immediately after the sole
  `--deployment-receipt` option.

`service-bind-task` requires a ready deployment, verifies its deployment receipt
live, and replaces only those values. It appends deployment id and canonical
deployment-receipt SHA-256 to the judge identity, then validates the complete
`kernelinfra.task.v1` result.

The template, task, and binding receipt must share a directory so relative task
paths retain exactly their original meaning. v0.7 requires exactly one service
stage; it never emits a partially bound task. Both output files use atomic
create-only writes and existing paths are never overwritten.

`kernelinfra.service-task-binding.v1` records template file/JSON hashes,
deployment/service identity, deployment receipt/path/hash, output task/path/hash,
stage id, and canonical binding hash.

service stage, stale live receipts, different template/output directories, and
same-path/overwrite output attempts. The FIBServe adapter now independently
requires the exact canonical deployment-receipt digest in task judge identity.

## Remaining boundary

The complete single-node campaign path is now automatic through explicit stop.
Kernel Infra does not yet count active task users or apply an idle grace period,
so it cannot safely auto-stop a ready deployment. Cross-host routing also
remains absent; a future dispatcher must select a node without taking ownership
of its broker queue, deployment history, judge results, or frontier.
