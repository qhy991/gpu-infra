## Evidence distinctions preserved

The release candidate maintains these non-interchangeable states:

- process completion versus run terminal state;
- correctness `valid`/`invalid` versus infrastructure `unknown`;
- valid result versus frontier eligibility;
- KDA authoritative speedup evidence versus generic absolute timing;
- kernel/leaf timing versus matched end-to-end service behavior;
- node lifecycle authority versus `mirror-only` downloaded bytes;
- live route observation versus allocation promise;
- production incompatibility versus absence of work.

No release claim should collapse these distinctions.

## Composed but not live-qualified end to end

The intended multi-agent GPU-reuse path is fully implemented as primitives:

```text
service-preflight
  -> service-start / bind one FIBServe deployment
  -> fleet-submit-many distinct candidates
  -> fleet-snapshot consumers
  -> fleet-collect terminal mirrors
  -> service-stop or idle grace releases one GPU
```

Its components have independent live evidence:

- earlier B200 managed FIBServe served multiple CPU-only consumers on one GPU;
- v0.14 performed one-probe, concurrent three-candidate B200 submission;
- v0.15 collected mixed then terminal evidence concurrently;
- v0.16 rejects stale broker/client deployments before mutation.

The complete current-version composition has not run on a real GPU. The latest
attempt correctly stopped at deployment compatibility/lock custody before any
GPU allocation. Therefore “v0.16 three-candidate FIBServe GPU reuse” remains
unqualified rather than inferred from component tests.

## Promotion gate

Before calling the repository production-live qualified or creating a release:

1. Obtain explicit authorization for production broker upgrade/restart.
2. Drain or otherwise preserve every production broker job and shared lock.
3. Install and verify exact agent-gpu-broker v0.6+ daemon and client.
4. Run `service-preflight` against the production paths.
5. Complete the real three-candidate FIBServe batch reuse workflow and prove one
   broker job/GPU, multiple consumers, terminal mirrors, and final release.
6. Restore A800 SSH and rerun at least current node/fleet/route smoke; do not
   substitute historical evidence.
7. Re-fetch current main, rerun the full suite and CI, then request explicit
   tag/release action.

Until those steps hold, the correct status is:

- implementation and evidence control plane: promoted to main;
- current B200 production managed-service composition: blocked externally;
- current A800 qualification: unknown;
- default branch: promoted;
- tag/GitHub release: not created.
